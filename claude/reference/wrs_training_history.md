## 0. まず用語

### 全体の構成

- **このプロジェクト:** 二足歩行ロボット（片脚5関節×2＝10関節、総質量約 10 kg）を、シミュレーションの強化学習で歩かせ、実機に載せる。当初の目標は坂を登ること。
- **シム（シミュレーション）:** NVIDIA の Isaac Sim / Isaac Lab。仮想のロボットを数千台同時に動かして学習させる。
- **WRS機:** 研究室の共用PC（GPU は RTX 3090 Ti、Windows 11）。学習はここで回す。作業は、WRS機上の Claude Code（別の AI）にユーザーが指示文を貼って進める。
- **Cowork（このチャット側）:** WRS機は直接触れない。WRS から来た報告を読んで判定し、次の指示文を書く役。
- **実機:** CubeMars 製のモーター（大きい AK10-9 と小さい AK80-9）を CAN 通信で動かす。制御はノートPCから。

### 関節の名前（片脚あたり、胴体側から順に）

| 略号 | 意味 | モーター |
|---|---|---|
| HR | 股のひねり（脚を鉛直軸まわりに回す＝爪先の向き） | AK10-9 |
| HAA | 股の開閉（脚を横に開く） | AK10-9 |
| HFE | 股の前後振り（腿を前後に振る） | AK80-9 |
| KFE | 膝の曲げ伸ばし | AK10-9 |
| FFE | 足首の前後の曲げ | AK80-9 |

名前の頭の LL は左脚、LR は右脚（例: LL_FFE＝左足首）。

### 学習の用語

- **方策（policy）:** 学習で作る「脳」。センサの値（観測）を入れると、各関節の目標角度（行動）を出す小さなニューラルネット。
- **観測:** 方策への入力。胴体の速度（前後・左右・上下の3つ。コード名 `base_lin_vel`）、胴体の回転速度、重力の向き（＝胴体の傾き）、指令、関節角、関節速度、前回の行動の計 42 個。
- **指令:** 「前へ 0.5 m/s、横へ 0、旋回 0」のような目標速度。学習中はランダムに与え、実機ではコントローラーから与える。
  - vx: 前後の速度 [m/s]
  - vy: 横の速度 [m/s]
  - wz（yaw rate）: 旋回の速さ [rad/s]。0.3 rad/s は約 17°/s。
- **heading モードと rel_heading_envs:** 指令の出し方は2通りある。
  - 「旋回の速さ wz を直接出す」
  - heading モード: 「向くべき方角を決め、今の向きとのずれから wz を計算して出す」
  - `rel_heading_envs` は、仮想ロボットのうち heading モードで指令を受ける割合。1.0 なら全部、0.5 なら半分。
- **env:** シムの中で同時に動かす仮想ロボット1台。学習は 4096 台、評価は 64 台。
- **iter（イテレーション）:** 学習の1回分の更新。3000 iter で1本の学習が終わる（2本同時で約 3.5〜4 時間）。
- **チェックポイント:** 学習途中の方策の保存。`@2999` は「3000 iter 目（0 始まりで 2999）の方策」。
- **run（ラン）:** 1本の学習。名前は中身の略（A_base0821、G_real_peak など）。
- **seed:** 乱数の種。同じ設定でも seed が違うと結果が揺れる。今回はほぼ seed 1本ずつしか回していない。
- **報酬:** 学習で「良い動き」に与える点数。速度指令に追従すると加点、転ぶ・関節を暴れさせると減点など。
- **std（探索ノイズ）:** 学習中、方策の出力にわざと足す揺らぎの大きさ。いろいろ試させるためのもの。評価・実機では使わない。`noise_std_type` はこの揺らぎを「そのまま持つ（scalar）」か「対数で持つ（log）」かの設定。
- **地形:**
  - 平地: 真っ平ら。
  - rough: 凸凹・坂・階段の混合。
- **ONNX:** 方策を実機のPCで動かすためのファイル形式。

### アクチュエータ（シムの中のモーターの模型）の用語

- **effort_limit:** 関節が出せるトルクの上限 [N·m]。実機では、AK10-9 は定格（連続で出せる）18・ピーク（短時間なら出せる）53、AK80-9 は定格 9・ピーク 22。ただし通信の方式（MIT モード）の都合で、AK80-9 に指令できる上限は 18。
- **stiffness / damping:** シムの関節の位置ゲイン（目標角からのずれにかかるバネ）と速度ゲイン（動きにかかるブレーキ）。実機モーターの Kp / Kd に当たる。実機では「指令した Kp」と「実際に効く Kp」の比が 0.538 と測れている。Kd の比はまだ決まっていない。
- **飽和率:** トルクが上限に張り付いていた時間の割合。
- **computed torque:** 上限で切る前に、モーターが出したがっていたトルク。
- **Kt:** 電流あたりのトルク。実機で未確定で、「指令したトルクの約 0.7 倍しか出ていない」可能性がある。

### 評価の用語

学習後の方策を、平地で決まった指令を与えて 64 台同時に 12 秒走らせる（最初の 2 秒は捨てる）。スクリプトは `measure_crab.py`。

| シナリオ | 与える指令 | 見たいこと |
|---|---|---|
| S1 | 前へ 0.5 m/s | 普通の前進（一番大事） |
| S2 | 前へ 1.0 m/s | 速い前進 |
| S3 | すべて 0 | その場で立っていられるか |
| S4 | 後ろへ | 後退 |
| S5 | 横へ 0.3 m/s | 横移動（前を向いたまま横へ） |
| S6 | 旋回 +0.5 rad/s（前進 0） | その場で回る |
| S7 / S8 | 前へ 0.5 ＋ 旋回 +0.3 / −0.3 | 歩きながら左右に曲がる（小旋回） |
| S9 | 旋回 −0.5 rad/s（前進 0） | その場で逆に回る |

判定の言葉（基準は事前に決めた）:

- **立ち往生:** 指令があるのに歩かない。S1 で前進速度が 0.35 m/s 未満、または止まっている台数が 5% 超。
- **カニ歩き:** 前進指令なのに横に流れる・斜めを向く。S1 / S2 で横速度 0.05 m/s 超、進行方向のずれ ±10° 超など。
- **転倒:** S1 で倒れた台数が 5% 超で不合格。
- **小旋回合格:** S7 / S8 で、指令どおりの向きに、0.15 rad/s 以上、左右の差が 2 倍以内で曲がる。
- **トルク合格:** S1 で、トルクの RMS（平均的な大きさ）が定格以下。
- **正規化 error_vel:** 学習ログにある「速度指令とのずれ」。そのままだとエピソードが長いほど大きく出るので、長さで割り直した値で読む。0.2 前後なら歩けている、0.7 前後なら止まっている目安。

## 1. 移設と、機体モデルの作り直し（09-13〜09-16 未明）

**何が起きたか:** それまで学習に使っていた Alienware（Ubuntu のPC）が 09-13 に故障した（数分〜十数分で電源が落ちる）。学習を WRS機に移し、09-15 に環境構築を終えた。
**問題:** GitHub には 08-21 以降のコードが push されていなかった。WRS機に来たのは 08-21 版のコードで、9月に Alienware で入れた報酬などの変更は失われている。

**機体モデルの作り直し:** CAD（Onshape）からロボットの設計図（URDF）を出し直し、シム用のファイル（USD）に変換した。この過程で大きな問題が2つ見つかった。

1. **シムの「前」がロボットの「横」だった。**
   - Isaac Lab は胴体座標の +X を前として速度指令を出す。ところが CAD の軸の都合で、+X がロボットの横を向いていた。
   - 旧モデルも同じだったので、過去の学習は「前へ進め」と言われて横に歩くことを覚えていた可能性が高い。これまで悩んでいたカニ歩き（横歩き）の最有力の説明。
   - 胴体の座標を 90° 回して直した。
2. **関節の回る向きが揃っていなかった。**
   - 左右で前後振りの向きが逆で、脚1本の中でも膝だけ逆向きだった。
   - 「同じ角度を入れると左右が鏡写しになる」「膝は人間と同じ向きに曲がる」ように5関節の軸を反転した。
   - 初期姿勢で股を 10° 開いていたのを 0 にし、出現させる高さを 0.376 m にした。

変換ツールの版の問題（ネット経由で取れない部品を、PC内の他人のキャッシュからコピーして解決）を越えて、試しの学習が動くところまで確認し、GitHub に push した（`6ede75b`）。約束事の正本は `reference/robot_model_conventions.md`。

## 2. 実験01: なぜ歩かない・なぜ横に流れるのか（09-16 早朝〜）

**背景:** 前の機体では「指令を出しても歩かない（立ち往生）」「歩いても横に流れる（カニ歩き）」が続いていた。前後の向きを直した今、何が足りないのかを確かめたかった。

**やったこと（2本を同時に学習、各 3000 iter）:**

- **A_base0821:** 08-21 版のままで、学習が落ちないように std の持ち方を log にしただけ。地形は rough。「向きを直しただけで歩くか」を見る対照。
- **B_combined:** A に「直す系の対策」を全部入れた。
  - 地形を平地にする。
  - 足を上げる報酬を二足歩行用のものに替える。
  - 速度追従の報酬の幅（std）を 0.5 → 0.35 に締める。締めると、横に流れたときの減点が効くようになり、立ち止まっているだけで貰える点も減る。

**結果:**

- A は 3000 iter 全部で、どの指令でも足を一度も上げずに立っていた（完全な立ち往生）。
- B は歩いた。前へ 0.5 の指令で 0.43 m/s、横流れはわずかで、転倒 0%。基準に合格した。
  - 弱点: その場旋回をしない（S6 で指令 0.5 に対し 0.03）。足が浮いている時間が 0.07〜0.11 秒と短く、すり足かもしれない。

**どれが効いたかの切り分け（追加で2本）:**

- C_noflat（B から平地だけを抜く＝rough に戻す）: 歩かない。
- C_flatonly（A に平地だけを足す）: iter 2400 で歩き出した。

**この段階で分かった読み違い:**

- 学習ログの「速度のずれ」はエピソードが長いほど大きく出る。長さで割り直すと、A は「途中で悪くなった」のではなく「最初から一度も歩いていなかった」。
- rough 地形の「初期難易度の上限」を上げると、易しくなるのではなく難しくなる。WRS側の案は採らなかった。
- 旧来の足上げ報酬は、この機体の小刻みな歩き方だと一歩ごとに減点になっていた。

## 3. 実験02: 地形・旋回・立てない件（09-16 昼〜夕）

**分かったこと1: 歩くか歩かないかの分かれ目は地形だった。** 平地なら 08-21 版の報酬のままでも歩き出す。報酬や std の違いは「歩き出すのが早いか遅いか」と「横流れの基準に入るか」にしか効いていない。実験01 の時点で書いた「平地と報酬の組み合わせが要る」は撤回した。

**旋回を覚えさせる試み:**

- **E_yawcmd:** B の設定で、指令の半分を「旋回の速さを直接出す」形にした（`rel_heading_envs` 0.5）。当時は「全部 heading モードだったので旋回の指令が出ていなかった」と読んでいた。結果、その場旋回は指令 0.5 に対し 0.06 で、覚えなかった。
  - 後の実験03 で指令を実際に数えると、heading モードでも旋回の指令は十分出ていた。「指令が出ていなかった」という読みも誤りで、方策の側が旋回を覚えていないだけ。

**坂への一歩:**

- **F_BtoRough:** 平地で歩けた B の続きから、地形だけ rough にして 1500 iter 追加。地形の難易度は 0.98 → 4.69 まで上がり、平地の歩行も保てた。ただし、まっすぐ前進の指令で円を描くように曲がる（0.32 rad/s）ようになった。

**立てない件:**

- 行動を 0（＝初期姿勢の角度を保持）にすると、ロボットは前に倒れる。
- Cowork は「関節のバネ（stiffness）が弱くて沈むから」と読んだが、4倍にしても 64台すべて前に倒れた。この読みは外れ。

## 4. ゴールの変更と合格基準（09-16 15時〜夕、ユーザー決定）

- **まず平地で実機を歩かせる。坂は時間が余ったら。** 実機は組み上がっている。
- **これまでの方策は実機に使わない。** シムのモーターの模型が実機より強すぎた。
  - AK80-9（定格 9 N·m）の関節に 20〜30 N·m を許していた。
  - 股の前後振り（AK80-9）を、膝（AK10-9）と同じ設定グループにしていた。
  - そこで関節ごとに実機のモーターに合わせた5グループに分け、一から学習し直す。
- **合格基準:**
  - トルク: S1 で平均的なトルク（RMS）が定格以下、最大がピーク以下。シムでは最大は上限で自動的に切られるので、飽和率と「切る前のトルク」も見る。
  - 旋回: 大きな旋回は要らない。ただし、向きを保つための小さな旋回はできること（S7 / S8 で判定）。
- 学習の同時実行は 2本まで（GPU の計算がすでに飽和していて、本数を増やしても合計は速くならない）。

## 5. 実験03: 実機に合わせたモーターで学習し直す（09-16 17:28〜21:12）

**2本を同時に学習（各 3000 iter、平地、指令の半分は旋回を直接出す）:**

- **G_real_peak:** トルク上限をピーク側に。AK10-9 は 53、AK80-9 は 18（通信で指令できる上限）。
- **G_real_rated:** トルク上限を定格に。AK10-9 は 18、AK80-9 は 9。

**結果:**

- **2本とも歩いた。** どのチェックポイントでも転倒 0%・立ち往生 0%、歩きながらの小旋回も合格。覚えるのも前の B より速い。
- **G_real_rated の問題:** 足首（FFE）が前進中に 20〜29% の時間、上限 9 に張り付いていた。切る前のトルクは最大 26.8 で、実機に指令できる 18 も超えている。
- **G_real_peak:** 足首の平均トルクは 7.0 で定格 9 以下、張り付きは 0%。
  - 3000 iter 目は横流れがわずかに基準を超えた（0.058 m/s、向き −14°）。2400 iter 目は 0.004 で問題なし。
- **判断:** G_real_peak をデプロイ候補にした。
  - 上限 18 が実機の指令上限と同じなので、シムと実機が一致する。
  - rated は「9 に張り付く歩き方」を覚えているが、実機は 18 まで出してしまうので、振る舞いがずれる。

**あわせてやったこと・分かったこと:**

- 方策を ONNX に書き出した（入力 42、出力 10、50 Hz）。観測の並びと単位の取り決めを `obs_contract.md` にまとめた。
- WRS機で学習が落ちる原因を特定した。Isaac Sim の部品と h5py というライブラリが同じ名前の DLL を持っていて、ぶつかっていた。起動手順を直した。
- 評価スクリプトが「トルク上限の上書き」を評価に反映していないバグを見つけて直した。
- 旋回の指令は十分出ていた（上の §3 の訂正）。
- 関節をほぼ固めても前に倒れる。初期の瞬間、片足は地面に 0 点、もう片足は 6 点でしか触れていない。左右のリンクの位置が、一律に 4 cm ずれて見える。

## 6. 実験04: 実機とずれても歩けるか（09-16 22時〜09-17 昼）

**考え方:** 実機はシムと完全には一致しない。

- トルクが指令の 0.7 倍しか出ないかもしれない。
- Kp / Kd の換算に誤差がある。
- 通信に遅れがある。
- AK10-9 の摩擦はまだ測っていない。

学習し直す前に、今の候補の条件を「評価のときだけ」ずらして、どこまで耐えるかを調べた。並行して、保険の学習も回した。

### 6-1. 停止点1（09-17 00:09）: 頑健性のチェック

G_real_peak の 2400 と 3000 iter 目で、16 通りの条件を試した。

| 条件 | 結果 |
|---|---|
| AK80-9 のトルク上限を 13.5 / 12（トルクが 0.7 倍しか出ない想定） | 合格 |
| 通信遅れ 20 / 40 ms、関節摩擦 2 倍、胴体 +1 kg、床の摩擦 0.5、センサ雑音、5 cm 上から吊り下ろし | 合格 |
| AK80-9 の上限 9（定格） | 2400 で転倒が増えて不合格（rated を選ばなかった判断の裏付け） |
| stiffness 0.7 倍 | 2400 で不合格 |
| damping 0.5 倍 | 両方で小旋回が不合格 |
| **damping 2 倍** | 両方で不合格。3000 iter 目は **64台すべて転倒** |

- ONNX の出力はシムの方策と誤差 1e-5 程度で一致した。観測の正規化は入っていない。
- **保険の学習の2本目の選び方で、Cowork の決めた規則が誤っていた。** 「上限 9 で不合格なら、上限 13.5 で学習し直す」という規則にしていたが、9 は定格でありトルク 0.7 倍の想定ではない（その想定の 12 は合格している）。規則どおり H_eff13p5 が選ばれたが、保険としての意味は小さかった。
- **左右 4 cm のずれ:** 胴体の原点が、左右の股の真ん中から横に 2 cm ずれているだけだった。原点を基準に左右を比べると、ずれが2倍の 4 cm に見える。WRS は「半分だけ説明できる」と書いたが、全部これで説明がつく。

### 6-2. 停止点2（07:11）: 保険の学習2本の結果

- **H_nolinvel（観測から胴体の速度を外して学習）:**
  - 狙い: 胴体の速度は実機では T265 というカメラ式センサから推定するしかなく、脚ロボットの着地の衝撃で狂いやすい。速度なしで歩けるなら、センサの要求が軽くなる。
  - 結果: **不採用**。
    - 前進 0.5 の指令で 0.315 m/s しか出ず、立ち往生の基準に届かない。
    - 横移動の指令では 78% の時間止まっている。
    - stiffness 0.7 倍で全台転倒。
  - → 実機では T265 の速度が必須と決まった。
- **H_eff13p5（AK80-9 の上限を 13.5 にして学習）:** G_real_peak とほぼ同じ合否で、足首のトルクが低い（平均 5.97 vs 7.04）。トルクが実機で足りない場合の備えになる。

### 6-3. 停止点3: 詳しい切り分け

- **damping 2 倍で倒れるのは、シムの計算上の不安定ではなかった。**
  - 計算の刻みを半分にしても 98% 転倒した。実機でも起こりうる劣化として扱う。
  - 実機の Kd の換算係数は、0.55 / 0.71 / 1.19 のどれかまで絞れている。モーターの速度レンジの資料が3通りに割れているため。
  - 仮に 0.55 として換算すると、実際に効く damping はシムの 1.0 倍・1.3 倍・2.2 倍のどれかになる。**2.2 倍なら転倒する側に入る。**
  - → 実機でこの係数を決めることが、デプロイ前の必須作業になった。
- **G_real_peak は胴体の速度に強く頼っている。**
  - 観測の速度を 0 にすると、前進でも旋回でも全台転倒する。
  - +0.1 m/s の誤差、雑音、100 ms の遅れには耐える。
  - → 実機では「T265 が外れたら止める」仕組みが必要。
- **足裏の傾き:** 初期姿勢で足裏が床に対して約 30° 傾いている。ロボット全体の重心は、足が床に触れている範囲（前後 15 mm 幅）より 73 mm 前にある。行動 0 で前に倒れるのはこれで説明がつきそう。
- **左右:** 胴体の原点のずれを除くと、左右の差は 1〜3 mm。足先側のリンクに、前後方向で約 1 cm の非対称が残る。
- **実機のコードを検証する材料を作った。**
  - シムで 500 step 歩かせたときの観測・行動・関節角・トルクの記録（golden npz）。
  - 実機用のモーター設定表。
  - 行動に上限の切り詰めは入っていないことを確認した。
- **H_gainDR** を 07:55 に学習開始した。学習のたびに stiffness を 0.7〜1.3 倍、damping を 0.5〜2.0 倍のランダムな値に振り、ゲインがずれても歩ける方策を狙う。

### 6-4. 11時前: H_gainDR の設定漏れ

- WRS の起動行の書き忘れで、H_gainDR だけ std の持ち方が scalar のまま学習されていた（他の run はすべて log）。そのため評価スクリプトが読み込めず、評価 11 本が全滅した。
- **判断: 評価のときだけ scalar で読み込んで続行。** std は学習中の揺らぎで、評価や実機で使う方策の出力には入らない。「このチェックポイントがゲインのずれで倒れないか」という候補選びの問いには影響しない。
- 残る留保: ランダム化の効果と、std の持ち方の違いの効果を切り分けられない。
- 再発防止: スクリプトが run の設定ファイルから自動で読むように直させ、起動時にこの設定を確認するチェックも入れさせる。
