## 1. ★2026-09-14 確定: 真因は「木の根の選ばれ方」

### 何が起きていたか

onshape-to-robot には**ドキュメント化された仕様**がある。

> The **first instance** in the assembly list will be considered as the base link
> （[Design-time considerations](https://onshape-to-robot.readthedocs.io/en/latest/design.html)）

修正前の 004_sim のインスタンス並び順の**先頭は `Part 1 <3>`**（右股回転モーターの出力側ブラケット、0.0649 kg）だった。この並び順は誰かが意図して決めたものではなく、**部品を挿入した順が残っていただけ。**

左右対称な木を `Part 1 <3>` を根にして辿り直すと、こうなる:

```
Part 1<3> ─┬─ LR_HAA → LR_HFE → LR_KFE → LR_FFE            右4関節・HR無し
           └─ LR_HR → 胴体 → LL_HR → LL_HAA → … → LL_FFE   左6関節・HR2段
```

**これは観測されていた URDF と1本残らず一致する。**

### 検証方法（Onshape API で実測。Alienware 不要）

ブラウザの Onshape セッションから Assembly API を叩き、Mate を全件取得して木を自分で組み直した。

- `GET /api/v6/assemblies/d/{did}/w/{wid}/e/{eid}?includeMateFeatures=true`
  → `rootAssembly.features[].featureData.matedEntities[].matedOccurrence` が「どのインスタンスを繋いでいるか」を返す
- Fastened 系 mate で union-find を組んで剛体グループ（＝link）を作り、`dof_` mate を辺として木を組む

**結果（修正前）:** インスタンス22 / `dof_` mate **10個ちょうど** / Fastened 11個 / 剛体グループ **11個**。
グループ同士の接続を**無向グラフ**として見ると、**URDF のそれと完全に一致した。違いは根の位置だけだった。**

### 決定的だった観察

**URDF を無向グラフに直して CAD と突き合わせる。** 親子の向きを外すと、根の選び方の違いと構造の違いが分離できる。
一致すれば「CAD は正しく、根だけずれている」、一致しなければ「CAD が違う」。今回は前者だった。

- **config.json に根を指定するオプションは無い**（公式オプション一覧を確認済み）。根は並び順でしか決められない。

### 9/08 の「メッシュが吸い込まれている」は観察としては正しかった

`lr_hr` のメッシュ体積 3200 cm³・bbox 29×13×18 cm・慣性 ixx が反対側の約30倍 —— これは事実だった。
**ただし解釈が逆だった。** 「胴体の形状が `lr_hr` に吸い込まれた」のではなく、**`lr_hr` という名前が付いていたリンクがそもそも胴体だった。** 根がずれていたので、胴体が脚の途中のリンクとして並んでいただけ。

同様に `base` が 0.2406 kg と軽すぎた件も、**`base` が胴体ではなく小さなブラケットだったから**で説明が付く。

## 4. なぜ8月から見逃されていたか（再発防止の本体）

**① 数え上げの検証は構造の誤りを検出できない。**
link 11 / joint 10 / revolute 10 / fixed 0 —— この4つは**根がどこにあっても目標通りの値になる。** 全部合格していたのに壊れていた。

**② ツールの暗黙ルールを確認しなかった。**
「最初のインスタンスが base」は公式ドキュメントに明記されている。誰も読まなかった。

**③ 手順書が異常を「正常」と明文化してしまった。**
旧 B2 の「一見『右脚が HR 欠け・左に HR 2つ』に見えても、本命 robot_sim.urdf と照合すれば同型と分かる」は、**自分の2つの版が同じ形だと確認しただけ**で、設計として正しいかの検証ではなかった。以後これが「正常の定義」として機能し、1か月生き延びた。

> **教訓:** 「2つの出力が一致する」は「正しい」ではない。照合先は**設計意図**であって、自分の別の出力ではない。

## 5. 症状（カニ歩き・立ち往生）の整理

構造の話とは別に、症状には3つの要素があった。ここは 9/06〜9/08 の分析が有効。

| 役割 | 何 |
|---|---|
| **原因** | 機体の左右非対称（上記の根ずれに由来）。現行データで横流れの81%が同方向 |
| **引き金** | 9/04 の前進限定化（`lin_vel_y=0` / `heading=0`）。横指令が許されていた間は癖に沿って動けたので露出しなかった |
| **増幅** | `track_lin_vel_xy_exp` 1.0→2.5、`track_ang_vel_z_exp` 0.5→2.0 |

### 立ち往生の回帰は数字で説明が付く

立ち止まったままで得られる1エピソードあたりの報酬（`値 × weight × dt(0.02) × 1000ステップ`）:

| | `track_lin` | `track_ang` | 合計 |
|---|---|---|---|
| 2週間前（weight 1.0 / 0.5、指令レンジ広い） | ≈ 1.8 | ≈ 3 | **≈ 5** |
| 現行（weight 2.5 / 2.0、前進限定・heading固定） | ≈ 22 | ≈ 37 | **≈ 59** |

**約12倍。** 立ち往生率 3% → 16% と整合する。
理由は2つの重なり。**①指令が小さく `heading` が固定されたので静止が「ほぼ満点」になった**（`exp(-誤差²/std²)` は誤差0で 1.0）。**②その上で weight を 2.5倍・4倍にした。**

### 横流れ測定の罠（再掲・重要）

2週間前は `lin_vel_y` 指令がランダムに出ていた。ロボットが横に動いたのは**指令に従っていたから**で、符号は指令と同じくランダムになる。**符号付き平均が0に近いのは当たり前で、機体バイアスの証拠にならない。**
**正しい指標は生の `v_y` ではなく残差 `v_y − cmd_y`。** 速度は胴体座標系（`root_lin_vel_b`）で取る。

## 10. 決定実験（学習ゼロ・play のみ）
