## 0. このチャットのゴール
- Jetson（Ubuntu / aarch64）で Switch 2 Pro コントローラーを読み、方策に渡す速度指令 (vx, vy, wz) を 50 Hz で作れるようにする。
- 安全装置（デッドマン、非常停止、途絶で停止、急な変化の制限）を込みにし、モーターを動かさない乾式テストで確かめるところまで。
- 制御ループ ver9（方策・CAN・T265 をつなぐ本体）への組み込みは、ver9 の形が決まってから。今回は「組み込める部品」を作る。

## 1. 最初にやること
1. `controller_next_chat_briefing.md` を先に読み、この文書と `next_chat_briefing_motor.md` の「状況の整理」「ファイルの場所」を読む。
2. Jetson 上のプロジェクト配置と Python 環境を確認する。パッケージ導入や既存のモーター制御コードへの変更は、この確認結果を受けてからにする。
3. USB 有線の実測は済んでいる。Bluetooth と Steam Input の調査はしない。

## 2. 前提として分かっていること
- **方策が受け取る指令:** 観測の velocity_commands は (lin_vel_x, lin_vel_y, ang_vel_z) の3つ、胴体（base）座標。学習時は3つとも ±1 の範囲で出していた。実値の範囲・並び・scale は WRS が作る `DEPLOY_README.md`（`D:\\Tominaga\\deploy_pkg\\20260918\\`）と `obs_contract.md` で必ず確認する（この文書の数字で決めない）。
- **評価で確かめた指令:** 前進 0.5 m/s（S1）、前進 0.5 ＋ 旋回 ±0.3（S7 / S8 の小旋回）。どちらもデプロイ候補 H_eff13p5@2999 で合格。
- **その場旋回 (0, 0, ±0.5) は H_eff13p5 ではできない。** 夜間の学習で旋回できる方策が出るかもしれないが、実験用（吊って見るだけ）。
- **ユーザーの要望（2026-09-17）:** 旋回ボタン (0, 0, wz) と並進ボタン (vx, vy, 0) を分けたい。「向きを変えて右へ行く」と「前を向いたまま右へ行く（横移動）」を分けたい。下がりながら回る動きもあってよい。
- **モーター側の注意:** 指令が途絶えるとモーターは最後の指令でトルクを出し続ける。だから「コントローラーが止まったら指令 0」だけでは足りず、ループ側が止める動作（ゆっくり止まる → 立つ姿勢 or 脱力）を能動的に送る必要がある。脱力の仕方は実機側（`next_chat_briefing_motor.md`）と合わせる。
- **速度観測（T265）が途切れたとき:** 直前値を保持し、0.2 s で停止動作に入る（学習側の評価結果）。コントローラーの途絶も同じ扱いに揃えるのが自然。

## 3. Jetson で確定した入力対応（2026-09-18 実測）

- Jetson: Linux 5.10.216-tegra / aarch64。
- USB 機器は `045e:028e`、入力名は `Microsoft X-Box 360 pad` として認識された。これは実機の表示名であり、Nintendo 名で見えないことは問題にしない。
- 安定パス: `/dev/input/by-id/usb-045e_XBOX_360_For_Windows_000000000001-event-joystick`（現時点では `event2`）。将来の実装は `event2` を直書きしない。
- 左スティック: `ABS_X` (code 0)、`ABS_Y` (code 1)、範囲 -32768〜32767。中立の実測は概ね X=0 / Y=-1、ドライバの flat は128。
- A: `BTN_SOUTH` (304)、Y: `BTN_WEST` (308)。そのほかの確認済み入力は chat 記録に残すが、本番操作には割り当てない。
- 左スティックは最大付近まで到達し、短時間の入力でもイベントは約1 ms間隔で来た。50 Hzの指令生成には十分だが、`pad_probe.py` で50 Hz出力と切断時の挙動を別途検証する。

## 4. Switch 2 Pro コントローラーの PC 対応（補足）
- USB 有線なら動くという情報が多い。Steam は Switch 2 Pro コントローラーに対応済み（Steam Input で XInput 相当に変換できる）。
- 無線（Bluetooth）は追加のドライバーが要るという報告がある。
- pygame（SDL2 ベース）で直接読めるかは不明。SDL3 系か、Steam Input 経由の XInput で読むのが候補。**どの経路で読めるかを最初に実測して決める。推測で実装しない。**

## 5. 進め方（この順。1段ずつユーザーの実測で確かめる）

### 実装状況（2026-09-18）

- Connect2USB2CAN の feat/mit-mode に pad_probe.py を追加済み（commit fab6eff）。左スティックを安定パスから50 Hzで読み、CSVと画面へ生値・正規化値・状態を出す。CAN、ONNX、モーターは使わない。
- Jetson上での実行、50 Hz周期、中立・最大値、USB抜線は未試験である。evdevが無い場合は導入方針を先に決める。
- この部品は teleop.py の代わりではない。デッドマン、非常停止ラッチ、変化率制限、ver9への受け渡しは次段階である。
1. **認識の確認（完了）:** Jetson で USB 有線認識と `evtest` による生値確認が済んだ。Windows / Steam の手順は今回の経路には使わない。
2. **読み取りの確認スクリプト `controller\\pad_probe.py`:** 使う経路（SDL / XInput / HID）で、全部の軸とボタンの生の値を 50 Hz で表示し、ログに残す。スティックの中立のずれ（デッドゾーンの決め方）、最大値、更新周期の揺れ、抜き差ししたときの挙動を実測する。パッケージを入れる場合は、どの Python に何を入れるかを先にユーザーに確認する。
3. **割り当ての決定（更新）:** 仮デプロイは左スティックだけで `(vx, vy, 0)` を出す。A / Y による時計・反時計回りの旋回は、直進方策には混ぜず将来の旋回方策の乾式試験まで保留する。左スティックを離したら指令は必ず `(0, 0, 0)`。非常停止はコントローラーの未使用ボタンに依存せず、物理的なモーター電源遮断を手元に置く。
4. **指令を作る部品 `controller\\teleop.py`:** 生の値 → デッドゾーン → 上限 → 変化の速さの制限（例: 0.5 m/s² 相当。値は吊り試験で決める）→ (vx, vy, wz) と状態（有効 / 停止 / 非常停止 / 途絶）を 50 Hz で出す。途絶（読み取りが 0.2 s 来ない・コントローラーが外れた）は停止扱い。すべてログ（時刻・生の値・出した指令・状態）に残す。
5. **乾式テスト（モーターなし）:** 画面に指令を出すだけで、各ボタン・途絶（ケーブルを抜く）・非常停止・デッドマンを1つずつ試し、ログで確認する。
6. **ver9 への渡し方の決定:** T265 は Python 3.10、ver8 は 3.13 で分かれている。コントローラーを同じプロセスに入れるか、別プロセスから UDP などで渡すかを、ver9 の構成と合わせて決める。別プロセスにするなら、受け手側にも途絶（0.2 s）で停止を入れる。

## 6. 最初の実機での上限（吊り試験用のたたき台。実機側と合わせて決める）
- vx 0〜0.3 m/s（後退は最初は無効）、vy ±0.2、wz ±0.3。評価で確かめた値（前進 0.5）より下から始める。
- 1モーター → 脚1本 → 全身の順は実機側の手順に従う。コントローラーは全身を吊ったときに初めて方策につなぐ。

## 7. やり残しになりそうなこと（このチャットで決めなくてよい）

- 立ち止まり (0, 0, 0) の指令で方策が安定して立っていられるかは、シムの S3 と吊り試験で見る
