# 2026-09-22 D9 1軸追従判定・USB再試行の修正

## 記録からの結論

- `gs_usb` の Python `ch=0` / `ch=1` は USB reset 後に入れ替わる。これは物理配線の反転ではない。D7/D9 は毎プロセスで全10 IDの受信から ID→ch を確定しており、`0x1C` だけへ送る D9 の送信先はその確定経路である。
- 直近の `0x1C` 指令は約 `-1.4`〜`-1.5deg`。既知の脚付き位置制御の不感帯は、実効剛性15で約 `1.4deg` である。`0x1C`（AK10-9）の摩擦は未実測なので、動かなかったことを ch 経路異常と断定しない。
- `GsUsbBus was not properly shut down` は、初回の USB open がライブラリ内部で途中失敗したときの `python-can` の finalizer 警告である。この経路で MIT は未送信で、アプリ側が既に開けたバスは再試行前に `stop_motors=False` で閉じる。

## 修正内容

- D7/D9 の各 USB open 間隔を 2.0 秒に延長した。二台目の gs_usb を起動する前の reset 復帰待ち不足による初回失敗を避けるためである。失敗時は従来どおり一度だけ、CAN送信なしで再試行する。
- D9 build `D9_RAMP_20260922_1705` は、選択1軸の量子化後 Kp/Kd/位置を `MIT wire check` として表示する。CSV は要求位置と実際に MIT パケットへ詰めた量子化位置を別列に残す。
- 1軸実行後、原点からの受信位置変化が `0.1deg` 未満なら `tracking abort` にする。零 MIT cleanup と CSV 保存は実行する。送信カウントだけで「位置制御成功」と誤判定しない。

## 次の実機操作の境界

この修正では目標位置・Kp・Kdを増やしていない。吊り支持・遮断担当・同じ通電中の D7 `oa`・D9 preflight がそろったときだけ、既存の `d9_2_1軸MITランプ_実験手順.md` の 0x1C 1軸コマンドを使う。`tracking abort`、異音、接触、支持ずれは主電源OFFで中止する。片脚・全身は未許可のままである。

## 実行結果（追記）

`D9_RAMP_20260922_1705` を 0x1C だけで2回実行した。各回で受信から確定した経路は `0x1C->ch1`、次回は `0x1C->ch0` であり、Python上の ch 番号が入れ替わった。一方で両回とも、量子化後の MIT 指令は Kp=7.937、Kd=1.233、初期位置約 -1.6deg、最終位置約 -2.1deg で402フレームまで送信された。

両回の `TRACKING` は 0.000deg で `tracking abort` となった。これは送信回数・ID経路・位置量子化の失敗ではなく、少なくともこの約2.1deg・現在のKpでは0x1Cのサーボ位置フィードバックが1 LSB（0.1deg）も変化しなかったことを示す。0x1C（AK10-9）の静止摩擦および必要なブレークアウェイ指令は未測定であるため、目標位置・Kp・Kdを増やして再試行してはならない。

保存CSV（402行）では、量子化後の位置は最終 -2.119deg、位置は全行 0.000deg、最大電流は |0.33|A、最大速度は 0.635deg/s だった。したがって D9 build `D9_RAMP_20260922_1715` は、無追従かつ |電流| >= 0.10A を `position stalled under load` と明示する。無追従かつ電流も小さい場合だけ、MITトルク応答未確認として区別する。この診断はトルクを追加しない。

USB open は各回で初回失敗後の再試行により成立し、`GsUsbBus was not properly shut down` が引き続き表示された。2秒のインターフェース待機では解消していない。`python-can` の gs_usb 初期化が途中失敗したときのライブラリ内部警告として扱い、CAN未送信の再試行後に10軸IDを一意に受信できなければ中止する。警告を隠す変更は行わない。

次の分離用として build `D9_RAMP_20260922_1725` に `--arm --static-probe` を追加した。これは方策パッケージとT265を開かず、D7原点から選択1軸だけへ相対位置をランプ・短時間保持する。位置上限は絶対値2.5deg、既存のKp/Kd・電流/速度/受信中止条件・零MIT cleanupをそのまま使う。0x1Cでの初回は -2.5deg、6秒ランプ、2秒保持とする。自動ゲイン変更・トルク前置・再試行は行わない。

完全吊り下げ・足の重なりなしで同プローブを3回実施した。開始後のD7では0x1Cのみ -0.3degで、他9軸は吊り姿勢に応じて原点から外れていた。初回は最大移動0.3deg・最大 |電流|0.34A、続く2回は最大移動0.0deg・最大 |電流|0.38A / 0.40Aだった。したがって、旧版が0.3degを `position tracking observed` と表示したのは誤りである。

build `D9_RAMP_20260922_1735` は、static probe の合格を「0.1deg以上」ではなく「要求相対角の50%以上（-2.5degなら1.25deg以上）」へ変更した。今回の全3回は `position stalled before target` と判定する。これは静止摩擦だけでなく、吊り姿勢の重力負荷・関節機構負荷も含む診断であり、これだけから増力・目標拡大を行わない。

static probe は0x1Cの現在フィードバックを基準にする相対指令であり、他9軸へMITフレームを送らない。完全吊り下げで他軸が原点から外れている場合、probeのためだけのD7 `oa` は不要である。D7 `scan 3`で全10 IDの受信と`err=0`を確認すればよい。全身方策を再開する条件とは別に扱う。

同じ吊り姿勢で方策ランプも再実行された。0x1Cは -0.3deg から初期方策目標 -6.4deg（差 -6.1deg）へランプし、量子化後も -6.402degまで送信された。CSVは402行で、実測位置は最大 -0.6deg（開始から0.3deg）、最大 |電流|=0.81A、最大速度=10.79deg/sだった。旧buildは0.3degだけで成功扱いしたため誤りである。

build `D9_RAMP_20260922_1745` は、方策ランプにも要求差の50%を追従条件として適用する。この実行なら必要移動は3.05degであり、0.3degでは `position stalled during initial policy ramp` として`tracking abort`になる。位置目標・Kp・Kdの自動増加はしない。

最終の同build方策ランプを2回実行した。最終CSV（`C:\Users\harut\Connect2USB2CAN\logs\d9_one_axis_0x1c.csv`、Git非管理）は2回目の402行で、開始 -0.6deg、初期方策目標 -6.5deg、量子化後最小 -6.534deg、実測位置変化 0.000deg、最大|電流| 0.85A、最大|速度| 0.95deg/sだった。直前の1回目も開始 -0.3degから目標 -6.4degへ送信し、位置変化0.000deg、最大|電流|0.88Aだった。両方とも`position stalled during initial policy ramp`で`tracking abort`し、0x1Cの送信経路は実行ごとに受信から一意に確定していた。

この結果により、同じD9方策ランプおよび同じstatic probeの再実行は保留する。次は実機送信をせず、CSV・AK10-9の実効ゲイン/摩擦記録・吊り姿勢の機構負荷を分析して、根拠のある次の1軸診断だけを別途決める。
