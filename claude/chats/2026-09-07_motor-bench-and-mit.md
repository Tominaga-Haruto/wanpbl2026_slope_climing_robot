## 1. 非常停止の方針を決めた

**議論の経緯:** 「遠隔緊急停止は作れるか」から始まった。

最初に提示した設計は4層（物理スイッチ／デッドマン／ウォッチドッグ／ソフト）で、
**「停止信号を送る」のではなく「生存信号が途切れたら止まる」向きにする**のが要点だった。
通信が切れた瞬間に止められない設計は、一番止めたい状況で機能しないため。

**ユーザーの判断: 遠隔緊急停止は作らない。非常停止＝電源を抜く。**

その判断に伴って残した設計上の含み:

- 電源はテザー給電と決まっているので、ロボットには常にケーブルが繋がっている。**無線の非常停止は不要。**
- **電源装置にリモートON/OFF端子があるモデルを選ぶ**と非常停止スイッチを直結できる。
- **動力系（モーター）とロジック系（将来の Jetson・IMU）を別ラインにする。**
  一発で全部落とすとログが消えて何が起きたか分からなくなる。
- 電源offの弱点は、遅い（0.5〜1秒）／脱力して崩れる／原点が飛ぶかもしれない（A3 未検証）／テンポが落ちる。
  日常的な停止はソフト（`x`）、電源offは最後の砦、という役割分担。

コード側もこれに合わせ、`x` の表示を「非常停止」から「停止」に変え、
**「本当の非常停止は電源を切ること」**を実行時とヘルプの両方に出すようにした。

## 3. ver4 を残して ver5 を作った

当初は `motor_console_ver4.py` を直接書き換えたが、**ユーザーの指示で ver4 を原状復帰し、ver5 を新規作成した。**
バックアップとの差分ゼロを確認済み。ver4 は新しい `cubemars.py` でもそのまま動く（廃止した定数を参照していないため）。

**ヘルプを全面的に書き換えた理由:** ユーザーから「`?` の説明に数字込みの例を入れてほしい、今は数字が伴っていないので分かりにくい」との指摘。
根本原因は**山括弧プレースホルダ**（`p <deg> [秒]`）で、これは手順書 A1 が「絶対に使わない」と定めているもの（実際に打ち込む事故が過去2回）。

全項目を「そのまま打てる数字入りの例」に置き換えた:

```
  ps 90 2000 5000 3     90度へ。最高2000ERPM・加速度5000ERPM/s で3秒
  c 0.8 0.3             0.8A を0.3秒 ⚠無負荷では暴走する
                        （実測: 起動しきい値は約0.63A、c 0.8 を1秒で約3回転した）
```

換算メモ（`1 deg/s = 31.5 ERPM` / `1.57 rad = 90 度`）と安全上限も追加。**MITだけ rad、サーボは deg** で単位が混ざるため。

## 4. MIT モード調査 — 誤判定と、その原因究明

### 4-1. 最初の `mprobe` が `ext` に ★ を付けた

3方式（std / ext / extid）に enable を送り、前後の受信フレームを比較する仕組みを作った。結果:

```
[ext] 送信 ID=0x82B DATA=FF FF FF FF FF FF FF FC
    サーボ形式(0x29xx)の受信: 50 → 0 フレーム
    ★ 新しい CAN ID が出現: 0x0000082B  data=ff ff ff ff ff ff ff fc
    ★ サーボ形式の定期フィードバックが止まった
```

**このとき「ext が本命」と読んだ。これは誤りだった。**

### 4-2. 手動の再現テストで否定された

健全なバスで同じことをやり直したところ:

| 打ったもの | 結果 |
|---|---|
| `mscheme ext` → `me` | 送信成功 |
| `hz 2` | **50.0 Hz のまま**（受信は止まっていない） |
| `send 32B 00 00 00 00` | **送信成功** |
| `raw on` | `0x292B` のサーボ形式が流れ続ける |
| `mit 0 0 0 0 0 1` | 位置も電流も動かず、応答フレームもなし |

**enable は何の効果も持っていなかった。**

### 4-3. 原因: gs_usb が送信フレームを受信ストリームに流していた

シャットダウン時の生ログが決定打だった。

```
[RX] ID=0x0000032B DLC=4 DATA=00 00 00 00              ← 自分が送った速度0
[RX] ID=0x0000082B DLC=8 DATA=7f ff 7f f0 00 00 07 ff  ← 自分が送った零トルクMIT
```

**`mprobe` が「新しい CAN ID」と報告した `0x082B DATA=FF..FC` は、自分が送った enable そのものだった。**

**修正:** `MotorBus._is_echo()` を追加。`msg.is_rx is False` か、直近 0.08 秒に送った (ID, データ) と完全一致するフレームを受信処理から除外する。除外数は `echo_count` に貯まり `mprobe` の出力にも出る。

### 4-4. エコー除外後の再測定で、真の原因が判明した

| 方式 | サーボFB | 除外したエコー |
|---|---|---|
| std | 50 → 50 | **1件** |
| ext | 50 → **0** | **12件** |
| extid | 0 → 0 | **1件** |

「新しい CAN ID」は消えた（エコーだった）。だが「50→0」は再現した。**そしてエコーの件数が答えだった。**

`send` は enable と disable の2回しか呼ばれない。**それが12件返ってきている＝同じフレームが繰り返し再送されている＝ACK が返っていない。**
ACK が返らないと CAN コントローラはエラーカウンタを増やし、error-passive から bus-off に落ちる。**落ちれば送信だけでなく受信も止まる。**

**⇒ 「サーボFBが止まる」のは MIT に切り替わったのではなく、こちらのコントローラが死んでいるだけ。**
その後 `o 1` で状態が19秒前まで古くなり、`q` で送信エラーが出たのも同じ現象。

### 4-5. 結論と、入れた対策

**A8 終了（否定）。CAN の宛先を変えても MIT には入れない。次は上位機ソフトの制御モード設定（B9）。**

`ext` は送るたびにバスを落とすので、**`mprobe` の既定の総当たりから外した**（`PROBE_SCHEMES_DEFAULT = [\"std\", \"extid\"]`）。
`mprobe 1 all` で明示的に含められるが警告が出る。`ext` で「50→0」が出た場合は ★ ではなく ▲ を出し、バスが落ちた結果だと明示するようにした。

### 4-6. ついでに見つかったバグ2件

1. **`parse_mit_reply` が受信ループから一度も呼ばれていなかった。** MIT が有効になっても状態が更新されない状態だった。`mit_rx` フラグで解釈するようにした。
2. **`stop_all` が MIT モードのモーターに効かなかった。** サーボ用の速度0フレームしか送っていなかった。enable を送った相手を記録し、零トルク MIT フレーム＋disable も送るようにした。**停止が効かないのは安全に直結するので優先で直した。**

さらに、コンソールの `MODEL` が `AK10-9` のままだった（ID43 の実機は AK80-9）。
ERPM 換算は両機種とも 31.5 で同じなので測定結果には影響しないが、**MIT のトルクレンジが ±65 と ±18 で 3.6 倍違う**ので指令が化ける。
既定を `AK80-9` に直し、`model` コマンドで実行時に切り替えられるようにした。

## 5. ベンチ測定 — 数値の確定

### 5-1. friction と armature（2回測定）

| | 1回目 | 2回目 | 採用 |
|---|---|---|---|
| クーロン摩擦 tau_c | 0.2140 | 0.2249 | **0.22 N·m** |
| 粘性摩擦 b | 0.01510 | 0.01127 | 0.013（ばらつき15%） |
| 出力軸慣性 J | 0.00979 | 0.00976 | **9.77e-3 kg·m²** |
| J ÷ データシート×81 | 1.08 | 1.08 | — |

**慣性は 0.3% で一致。** データシート比も2回とも 1.08 で、**「ロータ慣性 × 減速比²」という作り方が正しかった**と裏付けられた。

**friction で分かった重要な区別:** 従来の 0.54 N·m は起動しきい値 0.63 A から出した**静止摩擦**で、動摩擦ではなかった。
IsaacLab の `friction` は「動きに逆らうトルク」なので動摩擦 0.22 が正しい。**柱Aは倍以上厳しい条件で回していたことになる。**

初回の `coast` は失敗した（「減速区間が短すぎます」）。摩擦 0.22 に対して初速 120 deg/s では 0.1 秒ほどで止まり、
50Hz サンプリングで数点しか取れないため。**`--v0 500 --coast 6` にして成功。**

### 5-2. `p` と `ps` の差が数字で出た

同じ 90度移動を両方で実測（無負荷）:

| | `ps 90 2000 5000 3` | `p 0` |
|---|---|---|
| 最大速度 | 2040 ERPM（64.8 deg/s） | **26560 ERPM（843 deg/s）** |
| 最大電流 | 0.92〜1.02 A | **4.02 A** |

**一桁違う。** 脚を付けた状態や sim-to-real の追従検証では `ps` を使う。

### 5-3. フィードバックレート = 50.0 Hz ちょうど（A1 確定）

`hz 5` で 250フレーム/5秒、`hz 2` で 100フレーム/2秒。何も送らなくても流れる。

- **制御周期の上限は 50 Hz。** 送信も 50Hz なので状態は1周期に1サンプル。オーバーサンプリングの余裕はゼロ。
- **帯域は余裕あり。** 10モーターで 500フレーム/秒 ＝ 1Mbps の約 6.4%（A11 は問題なし）。

## 6. 新発見 — サーボ位置ループのリミットサイクル

**きっかけ:** 90度で保持したときだけ電流が上がり続け、0度では下がる、という非対称に気づいた。
「シャフトに何か付いているのでは」を疑い、**重力負荷なら電流は角度の sin に乗る**はずなので角度を振って確かめた。

| 保持角度 | 保持電流 | 挙動 |
|---|---|---|
| 0度 | −0.05〜−0.08 A | ほぼゼロ。完全に安定 |
| 45度 | 0.81 → 0.45 A | 減衰して落ち着く |
| **90度** | **0.4 ↔ 1.0 A を往復** | **15秒保持しても収束せず、約5Hz で振動し続けた** |
| 135度 | 0.44 → 0.63 A | 上昇して頭打ち |
| 180度 | 0.51 → 0.02 → 0.52 A | 下がってから上がる |

**重力負荷は否定された。** 180度なら sin がゼロに戻るはずが 0.5 A 残る。
`coast` の慣性も 1.08 倍のまま変わらず（質量が付いていれば増える）、`fric` も再現した。**何も付いていない。**

位置は 89.9〜90.0 deg（±0.05度）に張り付いたまま**電流だけが振動している**ので、これは**リミットサイクル**。

**最有力の解釈（未確定）:** 静止摩擦（0.54 N·m）とサーボ内蔵の積分項が噛み合ってスティックスリップを起こしている。
角度依存なのはコギングトルクの位相差と見ると辻褄が合う。

**なぜ効いてくるか:**
- 10モーターが姿勢を保持するだけで**アイドル電流が数A**（電源系 C5 の見積もりに入れる）
- 実機は常に微振動していて、方策が学習した「静止」とは違う
- **MIT なら Kp/Kd を自分で決められるのでこの積分項を避けられる。** MIT に移りたい動機がひとつ増えた

## 8. 終わらなかったこと

### Kt — 3回試して3回とも無効

**分銅を付けずに `--mass 0.5 --arm 0.1` を渡している。** 基準トルク 0.4903 N·m という前提が嘘なので結果に意味がない。
1回目 `Kt_out = 1.32`、3回目は0度で実行したため保持電流がほぼゼロになり `Kt_out = 55.7` と発散した。

**分銲と腕を物理的に取り付けない限り、このテストは絶対に測れない。**
これが残っている限り friction 0.22 はデータシート Kt 依存のまま（armature は電流を使わないので影響を受けない）。

### 恒久原点（A3）— 3回目の未達成

- 1回目: 電源を切らずプログラムを再起動しただけ
- 2回目: 同上
- 3回目: `o 1` の直前に `mprobe` を実行してバスが落ちており、状態が19秒前の値だった

**次は `mprobe` を先にやらないこと。** 順番は 起動 → `s` で生存確認 → `o 1` → `q` → **電源を切る** → 入れ直す → `s`。

### バックラッシュ — 測り方ごと未完

`ps 90` ↔ `ps 0` を何往復しても **行き 89.8〜89.9 / 帰り 0.0** で完全に再現し、ズレは 0.0〜0.1 deg。
**ただし内蔵エンコーダがローター側にあるなら、減速機の遊びは原理的に見えない。**
出力軸に目印を付けて外から測る以外に確かめる方法がない。

## 9. このチャックで学んだ進め方の教訓

1. **測定ツールが自分の送信を拾っていないか疑う。** 「新しい CAN ID が出現」は自作フレームのエコーだった。
   計測系そのものが嘘をつくケースで、**判定材料を2つ用意していたのに両方とも同じ原因で汚染されていた。**
2. **1回の測定は測定ではない。** friction / armature とも2回測って初めて数字として使えるようになった。
   逆に Kt は3回実行したが3回とも前提条件（分銲）を満たしておらず、回数では救えない。
3. **「変化があった」を「意図した変化が起きた」と読まない。** サーボFBが止まったのは事実だが、
   原因は MIT 有効化ではなくバス落ちだった。**変化の向きだけでなく、機序まで説明できるかを確認する。**
4. **エラーが出ないタイプの失敗が今回も出た。** 分銲なしの `kt` は正常終了して数字を出す。
   `ext` の送信も例外を投げない。**「成功したように見えるが意味がない」を疑う習慣が要る。**
